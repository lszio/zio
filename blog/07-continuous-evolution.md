# restart 之后还需要什么：让应用持续运行并演化自己的代码、模型与脚手架

日期：2026-10-15。设计解释，配合 [Groiz 对照评审](../docs/continuous-evolution-design.md)阅读。本文提出的联合快照、脚手架与自治采用机制仍是草案，没有实现或启动一个持续自我进化应用。

前一篇讨论了 Agent 怎样查询函数、运行实验，并在 condition 处选择 restart。现在再向前一步：如果 Agent 要长期运行，自己改代码、训练模型和调整工具工作流，restart 还够不够？

它解决其中一个重要问题，但需要另外几种机制共同工作。

## 1. 三个不同的“继续”

| 发生了什么 | 需要什么 |
| --- | --- |
| 处理第十条数据时缺值，程序仍停在有效恢复点 | condition/restart：给值、跳过或选择程序提供的恢复路径 |
| 训练到第 300 步，worker 被关闭，过一会儿换进程继续 | 训练 checkpoint 与持久任务：加载参数、优化器和进度，再开始新的执行 |
| 新算法评价更好，希望下一批请求使用它 | 版本切换与状态迁移：旧请求用旧版完成，新请求进入新版 |

不能把这三个问题都交给一个“重启”按钮。第一个通常保留活着的执行现场；第二个要从耐久存储恢复约定状态；第三个要决定新旧程序怎样共存。

Zio 当前静止镜像也有自己的边界：它保存支持的对象图，不代表能抓住任意执行中的原生栈或训练后端状态。相关基础见[编译器、VM、GC 入门](05-compiler-vm-gc.md)。

## 2. 自我修改应先产生候选

假设应用发现自己的排序函数在大输入上很慢。它可以读源码、生成新算法、编译并测试，但“生成文件成功”和“新版已经值得使用”之间还有距离。

比较应固定输入与资源条件，同时检查正确性、边界、旧任务回归与性能。若新程序只在一个样本上更快、遇到重复值就出错，当前服务应该继续使用旧版。失败实验也要记下来，避免下一轮又花同样代价重试。

因此，代码可以自由成为数据，运行中的稳定版本仍应有身份。候选是下一种可能，不应在产生时就改写正在服务的全局绑定。

## 3. 自己训练模型，需要保存比权重更多的东西

权重是训练已经学到的参数。继续训练时，优化器可能还保存“过去的梯度怎样变化”，采样器知道“数据读到了哪里”，随机数生成器也有自己的状态。

只加载权重可以开始一次新的训练，但不一定延续原来的训练轨迹。Groiz 的 CPU worker 就区分权重初始化和学习续接，保存参数、Adam 状态、CPU RNG 和 step，并检查可训练参数集合是否兼容。具体依据见[固定提交的 worker 源码](https://github.com/lszio/groiz/blob/33673b1e10ff8e5f43d244c4e1ed7a9d4e5c1d46/workers/torch/worker.py#L263)；本轮未重跑训练。

模型类型也要讲清楚：能够通过 API 调用某个大模型，不等于持有权重或能训练它。小模型训练、adapter 微调、蒸馏与完整模型训练应分别声明支持范围。

Zio 负责表达模型、训练方法和任务编排；高效张量计算可以由现有后端承担。让语言能组织训练，不需要先在 VM 里重写所有自动微分算法。

## 4. 脚手架也是程序的一部分

Agent 的能力不只来自模型权重。它先搜索还是先调用模型，怎样挑工具，怎样裁剪上下文，什么时候缓存，失败后重试什么，这些都会影响结果和成本。

例如一个候选把“每个问题都调用大模型”改成：先查本地知识库；已有可靠答案时直接返回；否则调用模型，并检查输出。这是工具工作流和上下文策略的变化，也就是这里讨论的脚手架变化。

要让它自己组装，这些结构就要能被读取、比较、编译和评价。描述中应包含工具签名、依赖版本、分支条件、恢复动作、最大轮次和资源需求。它可以在已授予的工具范围内探索；写一句“需要新工具”不会自动让宿主获得那个工具。

## 5. 为什么代码、权重与脚手架要一起版本化

新代码可能预期一个新的模型输出格式，新脚手架可能选择另一个工具，旧权重却只适配旧预处理。分别把三者切换到“最新版”，可能组合成一个从未被评价过的系统。

解决方向是一份可执行快照：它引用确切的代码、权重、脚手架、依赖和状态格式。大权重仍保存为二进制制品，不需要写进代码文本。评价绑定这个组合，而不只绑定某一个函数。

一次请求开始时固定快照 A；系统采用 B 后，新请求使用 B，旧请求继续引用 A，直到退出。否则一个长任务前半段使用旧预处理，后半段加载新模型，很难解释结果来自哪里。

如果 A 和 B 的业务状态格式不同，需要迁移或兼容窗口。切回旧代码不会撤回已经发送的消息，也不能自动把数据库恢复原样。

## 6. 持续运行靠任务账本和接管

单纯写一个无限循环并不能让系统长期可靠。进程会退出，worker 会失联，网络调用可能已经发生但回执丢了。系统需要记住哪个任务正在执行、谁拥有它、最近提交的进度，以及已经花掉的资源。

owner epoch 可以理解为每次接管获得的新任期编号；旧 worker 带旧任期提交结果时，不能覆盖新 owner 的进度。lease 是一段有效期，幂等键用来识别“这是同一个操作的再次投递”。它们是持久任务协议，不是 GC 或 restart 的另一种名字。

Groiz 已有相关队列、租约、计费和恢复代码可作参考。但源码评审也发现 canonical 入口的部分模型调用、评价与发布还只报未接线或返回回执，因此“有这些组件”不能当作“完整应用已经闭环”。[具体差距表](../docs/continuous-evolution-design.md)

长期运行还需要停下来：没有新反馈时 idle，配额耗尽时暂停，在新事件或下个授权周期唤醒。持续存在不等于持续消耗模型调用。

## 7. 自主程度应当由明确策略决定

一种模式是自动实验，所有正式采用人工确认。另一种是预先授权：某些模块、模型或脚手架在固定目标与预算内通过独立评价后，可以自动进入试运行，并在观察通过后采用。

后一种更贴近持续自主进化，但它不能靠伪造一条“人已批准”记录实现。应记录这是哪个策略、针对哪个候选、依据哪些评价作出的自动决定，并检查基础版本是否仍然相同。

候选可以改自己的工作方法，但如果同时任意改评价答案和通过门槛，就无法判断它是否变好了。评价和采用机制也能演进，只需通过与本次候选分开的版本流程。Groiz 目前正式采用仍有人工批准合同，自动采用在本设计中是待确认的新政策。

## 8. 第一轮真正值得演示的结果

一个小应用持续服务固定任务，自己完成一项代码优化、一次小模型训练或一次工具工作流改进。它保存候选与证据，在规定条件下采用新版，期间经历 worker 中断和服务重启；旧请求没有混版，失败候选没有覆盖稳定版。

最后用同一评价口径证明：任务完成率提高，或在质量不退化时降低成本。还要观察内存、磁盘、worker 和句柄是否正常回收。这比展示“它生成了一个更复杂的新版本”更接近自我进化。
