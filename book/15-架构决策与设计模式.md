# 15 - 架构决策：为什么这样设计

## 架构决策记录（ADR）

Zio 团队使用 ADR（Architecture Decision Record）记录每个重要决策。文件 `docs/adrs.md` 包含了从 v0.1 到现在的所有关键决策。

```
ADR 格式：
  标题：简洁描述（如"ADR-001: Sexp 与 Value 分离"）
  背景：为什么需要做这个决策
  决策：最终选择
  理由：为什么选这个方案
  代价：这个选择的成本和风险
  备选方案：其他被否决的方案
```

## ADR-019：当前收敛方向

本章保留早期 ADR 的机制说明与示意代码；完整现行决策以 [ADR-019](../docs/adrs.md#adr-019-grove-独立应用与同像性逻辑演化)、[语言架构](../docs/zio-architecture.md)和[Zio/Grove 基线](../docs/self-learning-architecture.md)为准，不以旧阶段编号、trait 摘录或固定内置数量判断当前交付。

- **语言核心**：ZOS 的 Object/Class/GF/Method/MOP 方向继续保留；核心收敛职责，不依赖 AI/Grove，也不以“其余皆库”排除对象系统。
- **Planned 自举**：展开、分析、编译逐步迁到 Zio，Rust 保留最小运行时、宿主边界与性能原语；用 Zio 写编辑器或 APP 不是编译器自举证据。
- **官方独立库与产品**：Numa（连续数值数组/矩阵/向量与后端接口）、Rill（参数/子命令/帮助、命令组合、终端 I/O 与退出状态，不承担语言求值）、Loom（模型/工具/会话/预算/取消/provider/ACP）按需安装、独立版本发布，不是语言内置特性。Grove 是消费语言与三库的独立 APP，持学习目标、实验、反馈、检查点、独立评价、人工批准、逻辑演化与 Web；核心无反向依赖，公共能力仅按真实复用抽取。
- **Planned 命名落点**：当前 `zio-ai`/`ai/` 是 Loom 的复用起点，`zio-cli`/`cli/` 是未来消费 Rill 的可执行宿主。三库新增能力未交付，正式短名不指定注册包 ID；未来规范目录与逻辑命名空间见[术语表](../docs/glossary.md)，现有代码、函数、包名和命令不改名。
- **Planned Grove 验收**：真实 LLM 生成代码，经解析、能力检查和隔离执行，错误与证据驱动修订；Web 展示源码、真实路径和 diff，反馈候选由独立评估与人工批准进入正式版本。自动训练与实验只能使用批准的预算和编辑范围，可信编译器/ZOS、鉴权、评估器、checkpoint 与发布守卫受保护。

同像性让逻辑可表示、可编辑，不使神经模型透明，也不替代执行验证。服务训练队列与静态 site 仍未构成上述闭环（agent 循环已在 G02 落地，但无 live 模型验收）；具体缺口及 ACP client/teacher-first、server-later 顺序见[实施计划](../docs/superpowers/plans/2026-10-05-zio-grove-convergence.md)。


## ADR-001：Sexp 与 Value 分离

### 问题

Lisp 需要"代码即数据"。宏处理未求值的代码，eval 处理运行时值。用一个类型还是两个？

### 决策：两个独立枚举

```rust
// 语法树 —— 不含运行时类型
pub enum Sexp { Nil, Boolean, Integer, Float, String, Symbol, Keyword,
                List, Vector, Map, Char }

// 运行时值 —— 包含函数、宏、对象
pub enum Value { Nil, Boolean, Integer, Float, String, Symbol, Keyword,
                 List, Vector, Map, Function, NativeFunction, Macro, Object }
```

### 理由

- 宏需要操作未求值的代码（符号保持为符号，别去环境查找）
- `quote` 需要将 Sexp 直接映射到 Value
- Rust 的类型系统保证两个域之间不混淆

### 你可以在代码中看到这个决策

打开 `sexp.rs` 和 `value.rs`——它们结构相似但类型不同：

```rust
// sexp.rs: 符号只是字符串
Sexp::Symbol("+")

// value.rs: 符号被求值后变成了函数
Value::NativeFunction(add)
```

## ADR-002：EvalContext + EvalEngine trait（消除全局变量）

### 问题

Zio 早期有 4 个 `thread_local!` 全局变量，导致：
- 测试不能隔离（一个测试改了全局变量会影响另一个）
- 不能嵌入多个解释器实例
- 无法 mock

### 决策

把状态放入 `EvalContext`，通过 trait 注入。

```rust
// 所有状态都在这里，没有 thread_local
pub struct EvalContext {
    pub env: Arc<Env>,
    pub modules: RefCell<ModuleTable>,
    pub loader: RefCell<Option<Box<ModuleLoader>>>,
}
```

### 结果

```
之前: 4 个 thread_local 全局变量
现在: 0 个 thread_local 全局变量
```

每个 `make_ctx()` 创建完全隔离的环境。测试可以并行运行。

## ADR-003：持久化数据结构

### 问题

Lisp 的默认数据结构应该是不变的。但用 Rust 的 `Vec` 做 `cons` 操作要 O(n) 克隆全列表。

### 决策：使用 im crate（持久化数据结构）

```rust
// value.rs
use im::{HashMap, Vector};

Value::List(Vector<Value>)     // 持久化列表
Value::Vector(Vector<Value>)   // 持久化向量
Value::Map(HashMap<Value, Value>)  // 持久化哈希表
```

持久化数据结构通过**结构共享**实现 O(log n) 的 cons/car/cdr 操作。

### 代价

- 比 `Vec`/`HashMap` 慢 2-5x（对小集合不明显）
- 迭代顺序不确定（HashMap）
- 索引访问 O(log n) 不是 O(1)

## ADR-004：Span 嵌入 Sexp

### 问题

错误消息长这样：`"error: symbol not found: foo"`——没有文件、行、列信息。

### 决策

给 Sexp 每个变体加 `Option<Span>`：

```rust
pub enum Sexp {
    Integer(i64, Option<Span>),
    Symbol(String, Option<Span>),
    List(Vector<Sexp>, Option<Span>),
    // ...
}
```

### 结果

错误消息可以变成：

```
error: symbol not found: foobar
  ┌─ program.zio:3:5
  │
3 │   (foobar 42)
  │    ^^^^^^ symbol 'foobar' not found
```

## ADR-005：EvalEngine 拆分为子 trait

### 问题

原来一个 `EvalEngine` trait 有 8 个方法，混合了求值、模块、ZOS 功能。嵌入场景（只需要求值）需要 mock 不需要的方法。

### 决策：三个独立 trait

```rust
// 只要 eval 能力
pub trait EvalRuntime {
    fn eval_expr(&self, ...) -> Result<TailResult, EvalError>;
    fn env(&self) -> &Arc<Env>;
}

// 需要 ZOS 对象系统
pub trait ZosRuntime: EvalRuntime { ... }

// 需要模块系统
pub trait ModuleRegistry { ... }

// 三者合并，方便使用
pub trait EvalEngine: EvalRuntime + ModuleRegistry {}
```

### 嵌入场景

```rust
// 只需要 eval，不需要模块、ZOS
struct MyEmbed { env: Arc<Env> }
impl EvalRuntime for MyEmbed { ... }
// 够了！不需要实现 ModuleRegistry 和 ZosRuntime
```

## ADR-006：Value::Object 作为 ZOS 入口

### 问题

ZOS 需要支持堆分配的运行时对象（Instance、Class、GF、Method），但这些类型在编 Rust 编译期无法全部预知（MOP 可以让用户创建新类型）。

### 决策：新增 `Value::Object(Box<dyn ZosObject>)`

```rust
pub trait ZosObject: std::fmt::Debug {
    fn header(&self) -> &ObjectHeader;
    fn as_any(&self) -> &dyn Any;
    fn clone_box(&self) -> Box<dyn ZosObject>;
}

pub enum Value {
    // 所有现有类型保持内联
    Integer(i64), Float(f64), String(String), ...
    // ZOS 入口
    Object(Box<dyn ZosObject>),
}
```

通过 `as_any()` + `downcast_ref` 可以安全地访问具体类型。

## 决策模式总结

Zio 的决策风格可以总结为几个模式：

| 模式 | 例子 | 说明 |
|------|------|------|
| **拆分为独立类型** | Sexp vs Value | 不同的域使用不同且不混淆的类型 |
| **Trait + Context** | EvalEngine + EvalContext | 状态集中，行为通过 trait 注入 |
| **持久化数据** | im crate | 不可变是默认，结构共享是优化 |
| **开放扩展** | Value::Object(dyn ZosObject) | 可预见需要扩展的地方使用 trait object |
| **分层设计** | EvalRuntime / ZosRuntime / ModuleRegistry | 嵌入者只实现需要的部分 |
| **职责收敛** | Zio/ZOS 与工具链 / Numa、Rill、Loom 独立库 / Grove 独立 APP | 保留 ZOS 核心，无反向依赖；真实复用才抽取，不用固定数量定义核心 |
