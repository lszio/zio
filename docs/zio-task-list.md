# Zio 后续任务清单

更新：2026-10-16。范围：语言、编译器、执行器、开发工具、通用库与发行。

> **任务执行入口在 paca：zio 项目（P0/P1/P2 Epic + ZIO-001～025 任务）。** 本文件保留为规划全文镜像；任务状态、排期与后续增改以 paca 为准。

这是聚焦 Zio 的待办入口，按依赖安排工作；不是本轮实现记录，也不代表设计草案已全部采纳。已采纳的工具链合同和历史验收继续以[工具链工作包](superpowers/plans/2026-10-11-zio-language-toolchain.md)为准。涉及语义变更的任务，先完成设计取舍，再形成该子系统的实现计划。

当前目标：**让人和 AI 都能查询、编译、执行、诊断和修复 Zio 程序，再把这套能力做成长时间运行、可安装、可复现的语言生态。**

## 1. 聚焦边界

| 层次 | Zio 要交付什么 | 归属 |
|---|---|---|
| 语言 | 明确语义、宏、模块、结构化条件与 restart | `langs/` |
| 编译与执行 | 复用已有编译器、自举、VM 和镜像；补齐一致性、内存与生命周期 | `langs/` |
| 开发工具 | help/查询、执行 harness、MCP、项目工具、LSP、调试与诊断 | `langs/`、`contribs/` |
| 库 | 标准库、通用任务/消息/存储接口、计算与模型后端适配 | `libs/`、`contribs/` |
| 发行 | 完整开发安装、包依赖、版本兼容、多目标应用产物 | 工具链与发行脚本 |

Groiz 的目标规划、候选评价、自动采用政策、训练策略和实例协商，由 Groiz 自己管理。Zio 提供它们需要的通用能力；只有跨应用复用得到证明的机制才下沉，不把“先完成 Groiz”作为语言发行前提。

## 3. 第一批任务

建议按下面的顺序启动。每一项都有独立交付物；第 2～4 项在基线清楚后可以分别推进。

- [ ] **ZIO-001：核实现状，建立唯一状态表。** 区分已验收、部分实现、待实现、待设计；记录证据版本和重跑入口，修正文档中的陈旧表述。
- [ ] **ZIO-003：确定查询元数据合同。** 先让 AI 能找到函数、签名、文档、模块和示例，并能判断某能力是否可用。
- [ ] **ZIO-005：确定 condition/restart 最小语义。** 用“读入失败后提供替代值继续执行”的例子说明 handler、restart 和清理过程，覆盖三条执行路径。
- [ ] **ZIO-007：确定执行 harness 合同。** 明确会话、编译/执行、输出、预算、取消和错误的生命周期，列清宏展开与宿主调用的限制。
- [ ] **ZIO-010：确定 GC 与资源生命周期方案。** 先画清哪些对象必须保持存活，再选择回收方案；不要直接通过弱引用改写闭包语义。

这一批先消除实现所依赖的不确定性。暂不同时开展 JIT、完整 MOP、分布式 VM 或模型训练框架。

## 4. 按优先级排列的任务

优先级是推进顺序：P0 为当前基础与 AI 闭环；P1 为可靠运行与可交付工具链；P2 为生态扩展。设计任务的验收是可评审合同；实现任务的验收是可运行行为。以下新增任务均未在本清单中标记完成。

### P0：明确语义，打通 AI 使用闭环

| 编号 | 任务与起点 | 前置任务 | 验收条件 |
|---|---|---|---|
| ZIO-001 | 状态与证据基线；复核旧工作包、评审和公开文档 | 无 | 每项状态可追溯到源码/历史验收；本次实跑与历史记录分开；找出需要重跑的缺口 |
| ZIO-002 | 语言语义分批定案；基于 D01–D08、D12–D18 | ZIO-001 | 绑定/赋值、真假、模块、宏阶段、数值/相等性、集合/ZOS、制品版本分别有取舍、兼容与迁移说明；每批采纳后补 AST/元循环/显式 VM 对照，不等全部议题结束才交付 |
| ZIO-003 | 查询元数据设计；统一源码文档和 native 注册信息 | ZIO-001 | 明确 help、describe、apropos、模块导出与能力查询的结果结构、来源、版本及未知状态；查询不执行被查询代码 |
| ZIO-004 | 实现结构化查询及 REPL 展示 | ZIO-003 | 人可阅读，agent 可消费结构化结果；函数、宏、模块、native、缺失文档都有一致行为；示例可定位到当前版本 |
| ZIO-005 | 最小 condition/handler/restart/cleanup 设计；D09 | ZIO-001 | 明确动态作用域、handler 选择、restart 参数及可见范围、返回/退出与清理顺序；区分同步处理和跨请求暂停；给出三种执行器的实现边界 |
| ZIO-006 | 实现同步本地 restart 与错误诊断 | ZIO-005 | 出错时在可恢复状态仍存在时选择 restart；替代值、重试、放弃、嵌套处理、清理均有行为用例；不同执行路径一致，错误带源码位置 |
| ZIO-007 | 执行 harness 设计；D20 | ZIO-001 | 定义会话/运行标识、能力、编译与运行结果、输出、事件、预算、取消、关闭；覆盖 reader/宏展开/编译/VM/native 各阶段的限制，不能取消的调用有明确隔离策略 |
| ZIO-008 | 实现最小 harness | ZIO-007 | 可新建会话、编译、运行、读取结果/诊断、取消及释放；能捕获输出；失败后会话行为明确；保留大整数等值的精度，不依赖字符串解析错误 |
| ZIO-009 | 解释器 MCP 基础服务；D21 | ZIO-004、ZIO-008 | 本地 stdio 可查询、编译、执行和关闭会话；复用同一 harness；stdout 仅协议流；会话不依赖传输连接身份；首版明确声明不支持远程 restart |

ZIO-002 按议题分批落地，不成为全部工作的总闸门；某项修改语义时，必须先通过对应议题的合同。ZIO-009 可先提供有限寿命、有限预算的会话，不必等待完整 GC；它不因此获得“长期可靠运行”的完成状态。

### P1：长时间运行、开发体验与发行

| 编号 | 任务与起点 | 前置任务 | 验收条件 |
|---|---|---|---|

| ZIO-015 | JS 宿主与编译路径一致性；续接 J01 | ZIO-001 | native/browser、AST/编译路径对显式绑定、类型转换、精度、错误和能力限制有对照；浏览器 Worker 超时与终止有真实验收 |
| ZIO-016 | 完整开发发行；续接 D00 | ZIO-001、ZIO-015 | 在声明支持的系统干净安装；解释器、编译器、同版本 LSP、语法资源、WASM、文档及许可证齐备；普通用户不依赖源码检出和 Rust 开发环境 |
| ZIO-017 | 多目标产物和发行回归；续接 A01/A02/D01 | ZIO-016 | native、真实浏览器、WASI 按支持矩阵实跑；浏览器资源闭包和离线约束明确；WASI 区分 runtime/payload 与单应用产物；缺证据的平台不标已支持 |
| ZIO-018 | 标准库合同与可发布库样板；D08/D17 | ZIO-013、ZIO-014 | 划清核心/标准库/官方扩展；补字符串、集合、序列、错误、I/O 等实际缺口；至少一个库可独立安装、生成文档、测试和升级，不重复新建已有库 |
| ZIO-019 | 调试、追踪和性能基线；D16 | ZIO-008、ZIO-010 | 可定位源码/宏展开/VM/native 失败；可观察运行、内存、句柄和取消；建立可复现基准后再决定优化，不把执行轨迹等同于确定性重放 |
| ZIO-020 | 版本绑定与稳定发行政策；D13/D18/D23 | ZIO-002、ZIO-011、ZIO-017、ZIO-018、ZIO-019 | 制品/模块/镜像兼容版本明确；旧会话的代码绑定不被全局热替换悄悄改变；升级/拒绝/迁移策略可验收；发布前检查清单可执行 |

长期运行的“恢复”分三种：本地 restart 是处理当前条件；暂停/恢复是保留活动执行状态；进程重启后的持久任务恢复是根据日志/检查点重新调度。ZIO-012 不自动交付第三种，也不把已有静态镜像当作活动栈快照。

## 7. 任务执行与开发流程（paca 驱动）

**paca zio 项目是唯一的任务入口**（Epic：P0/P1/P2；任务：ZIO-001～025，均含前置任务与验收条件）。仓库内不建并行的本地待办清单；本文件与 paca `Planning/Zio 任务清单` 互为镜像，任务状态、排期与增改以 paca 为准。

### 7.1 任务生命周期

1. **领取**：开始前从 paca 取任务（`list_tasks` / `search_tasks`），确认任务描述里的前置任务已满足、验收条件可验证。找不到对应任务的工作 → 先在 paca `create_task` 再动手。
2. **进行**：`update_task` 置状态 **In Progress**。切片子任务挂在 paca 原任务下（`parentTaskId`）或记入任务评论；不在本地另起执行清单。
3. **进展**：关键节点用 `add_task_comment` 记录证据：文件范围、兼容影响、commit、实测命令与结果、环境/版本。
4. **验收**：对照验收条件实跑，满足后 `update_task` 置 **Done** 并在评论附验收证据；无法实跑的目标保持待验收，不标完成。
5. **新任务**：直接 `create_task`（按 §4 格式：任务与起点/前置任务/验收条件），挂到对应优先级 Epic 与里程碑 tag；新任务编号顺延 ZIO-0NN。

### 7.2 执行纪律

每个实现任务开始前，确认对应设计已采纳，写明文件范围、兼容影响和有意义的验收。按仓库要求先做图谱影响分析（GitNexus `impact` / `detect_changes`）；改完运行相关检查，提交前分析图谱变更。完成记录注明版本、环境和结果。

任务内同步更新相应参考文档与示例。涉及编译器、VM、GC、restart、暂停或版本绑定的设计，补入已有博客，用“解决什么问题 → 一个小例子 → 内部如何工作 → 边界与代价”的结构解释，避免另开一条脱离实现的博客待办。
